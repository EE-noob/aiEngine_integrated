# 设计报告写作知识库

本文档汇总《基于 PicoRV32 与优化 NPU 的异构处理器设计报告》的写作约束、术语规则、章节组织和语言风格要求。后续修改报告时，应优先遵守本文档，并结合 RTL、驱动、仿真日志、综合报告和报告正文中已经确认的客观结果进行更新。

## 1. 文档定位

设计报告应作为最终技术报告呈现，不写迁移过程、版本替换过程、迭代记录、编写依据说明或资料整理痕迹。报告正文只讲设计本身，表达方式应体现该系统是完整设计结果，而不是基于旧项目改写得到的说明材料。

报告内容应面向应用背景、需求和设计目标展开，开头不应以“新赛题”“旧报告迁移”“当前材料”等表述组织。若需要记录修改过程、验证日志、草稿说明或素材来源，应写入单独文件，不能写入正式设计报告正文。

设计报告侧重系统架构、模块设计、软硬件接口、设计特色、性能优化、性能分析和实现结果总结。验证方法、验证日志、覆盖率、运行输出和测试通过记录应放入独立验证报告，设计报告中只在必要处引用已确认的性能结果和实现指标。

## 2. 章节组织规则

第 1 章应短而集中，按以下小节组织：

| 小节 | 内容要求 |
|---|---|
| 1.1 设计场景及应用背景 | 简要说明端侧推理、矩阵计算、CPU 与 NPU 协同的背景，不写过长背景铺垫。 |
| 1.2 设计目标 | 说明功能目标，包括 PicoRV32 控制、AXI-Lite 寄存器接口、AXI4 数据访问、TFLite Micro/NMSIS-NN 支持、WS/IS 数据流切换、s8 与 s16 输入支持、bias 和 per-channel 参数支持等。该节不写评测指标。 |
| 1.3 设计内容简述 | 用简洁段落概括系统组成、NPU 数据通路、软件接口和主要实现内容。 |
| 1.4 设计快速概览 | 使用 bullet 形式集中说明设计特色、支持功能和实现结果概况。首次出现的配置必须写清楚含义，不直接使用未解释的缩写。 |

系统架构相关内容统一放入“系统架构设计”大章。原本分散的系统组成、处理器与 NPU 协同、AXI 总线和 NPU 总体结构应合并到该章，并配套结构图。模块设计章节应覆盖真实 RTL 中存在的模块，不介绍已经删除或不存在的模块。

软硬件接口相关内容合并为一个大章，下设寄存器、指令与软件接口、驱动接口、TFLM/NMSIS-NN 接入、算子映射和规格汇总等小节。报告不得写自定义 RISC-V 指令，因为当前设计使用 AXI-Lite 寄存器组和 AXI4 数据访问接口。

“设计特色与性能优化”章节只介绍真正关键的设计特色，包括分块矩阵外积式数据流调度、IA cache 复用、权重驻留、部分和缓冲区、分块DMA、总线仲裁、预取、反压局部化、参数化设计和 WS/IS 双数据流支持。不保留泛化、重复或类似注意事项的内容。

“性能分析”作为单独大章，包含系统吞吐量分析、总线利用与数据供给匹配分析、软硬件推理对比等内容。实现结果总结应放在最后，用于陈述已实现功能、赛题要求对照、资源与性能指标，不使用“项目交付”式表述。

## 3. 模块设计写法

所有“模块设计”相关小节应采用正式数字 IC 设计说明风格，重点描述模块功能、结构组成、接口关系、时序行为、控制状态、寄存器配置或参数配置。模块设计小节建议采用以下结构：

```text
X.X 模块名称模块设计
X.X.1 功能说明
X.X.2 结构组成
X.X.3 接口定义
X.X.4 工作流程与状态机
X.X.5 时序行为
X.X.6 寄存器与配置说明
```

若模块没有软件可见寄存器，不写“寄存器与配置说明”，改写为“参数配置说明”。参数配置说明应列出综合期参数、运行期输入控制信号和内部状态寄存器的作用，不把普通 input 信号误写为参数。

有状态机的模块需要给出 Mermaid 状态机图。状态机描述必须明确状态名称、状态含义、进入条件和跳转条件，例如“当 start 信号被采样为高且配置寄存器 valid 位为 1 时，状态机由 IDLE 进入 CONFIG”。不得使用“自动处理”“智能判断”等不确定表述。

接口表建议包含“信号名、位宽、方向、时钟域、功能描述、备注”。功能描述应说明有效电平、保持条件、握手关系、采样时刻和使用约束。valid/ready、req/ack、AXI-Lite、AXI4、DMA 读写请求、字节写掩码、响应完成条件等关键接口必须补充时序说明。

## 4. 语言风格

正文使用严谨、客观、工程化的数字 IC 技术文档语言。句式以“本模块……”“该单元……”“当……时……”“在……条件下……”“复位后……”“状态机由……进入……”为主。每个自然段围绕一个明确主题展开，描述功能时说明输入、处理和输出，描述结构时说明组成、职责和连接关系，描述时序时说明采样、保持、更新和完成条件。

不得使用第一人称，不写“我们设计了”“可以看到”“本文基于某些资料”“当前性能材料”等表达。不得使用口号式总结、营销化表述、过度概括的 AI 生成文本风格或口语化连接词。避免“提升体验”“增强能力”“高效赋能”等非硬件文档表达。

报告正文中禁止出现以下词汇：`链路`、`实践`、`口径`、`闭环`、`边界`、`收敛`、`签核`、`映射`、`量化`、`判据`、`归约`。其中 `收敛` 仅允许出现在固定搭配 `时序收敛` 中。若需表达相关含义，应改用更规范的技术表述，例如：

| 禁用表达 | 建议替代表达 |
|---|---|
| 链路 | 数据通路、连接路径、传输路径、访问路径 |
| 实践 | 实现方式、设计实现、工程实现 |
| 口径 | 统计范围、定义方式、计量方法 |
| 闭环 | 完整控制过程、反馈控制、控制回路 |
| 边界 | 范围、限制条件、接口分界、地址范围 |
| 收敛 | 稳定、满足条件；仅“时序收敛”可保留 |

正文不使用 `beat`，统一改为“数据拍”。不使用“lane mask”这类模糊英文描述，应写成“有效通道标志”“字节写掩码”“有效列标志”等中文技术表述。

## 5. 术语与命名

统一使用 NPU 表述，不使用 MMA 指代当前模块。模块层级应以最终 RTL 为准，使用 `npu_top`、`npu_axil_top`、`npu_axil_reg_if`、`npu_controller`、`ia_loader`、`kernel_loader`、`bias_loader`、`compute_core`、`vec_requant`、`vec_s8_to_fifo`、`oa_writer`、`axi_block_dma_arbiter`、`axi_dual_block_dma` 等真实模块名称。

报告正文尽量避免直接使用 `S16`、`C4`、`SIZE=16` 等首次出现时不易理解的简称。应写成“16x16 阵列”“4 个 IA cache 分块”“阵列规模为 16x16”“IA cache 块数为 32”等清晰表述。若在表格或参数说明中必须使用 `SIZE`、`IA_CACHE_BLOCKS` 等 RTL 参数，首次出现处必须解释其含义。

`bias`、`per-channel`、`IA cache`、`TFLite Micro`、`NMSIS-NN`、`AXI-Lite`、`AXI4`、`valid/ready`、`WS/IS` 等常用技术术语可以保留英文或英文缩写，但首次出现应结合中文解释。`Invoke()` 不写入正文，统一表述为“推理”或“推理周期”。

不得出现“数据面”“控制面”“存储面”这类不够规范的泛化表达。可按上下文改为“计算数据通路”“控制寄存器接口”“存储子系统”“片上缓存结构”等具体表述。

## 6. 性能与实现结果写法

性能数据必须使用实测结果，不能用理论数值替代实测数值。若写理论上限，必须明确标注为“理想情况下的算力上限”，并与实测吞吐分开说明。TOPS/GOPS、周期、利用率、资源、频率、时序余量等指标不得编造；若输入信息没有提供，应写“该指标需结合综合或仿真结果进一步确认”。

性能分析需要说明实验条件，包括阵列规模、IA cache 分块数、部分和帧数、任务规模、AXI 数据宽度、折算频率、固定 cache 容量或固定 cache 块数等。固定 IA cache 块数实验可采用较大的块数，例如 32 块，并明确这是模拟实验条件，实际硬件实现可能消耗大量资源。

阵列规模扫描可覆盖 4x4、8x8、16x16、32x32 和 64x64 阵列。若分析 1TOPS，应同时说明理想上限、实测吞吐和实现难度。对于 64x64 这类大阵列，若实测结果显示性能受限，应总结为总线带宽限制，并说明数据供给、分块切换、权重装载和写回排空共同制约有效吞吐。

总线利用率分析应说明 IA cache 深度与外部访问次数的关系。由于 cache 复用提高后读数据拍减少，总线利用率可能下降，这不一定是不利结果。总线利用率不能单独代表性能优劣，应结合总周期、读写数据拍、阵列利用率、FIFO 等待、加载等待和写回等待共同分析。

低功耗内容不写入报告，因为当前设计没有做相关实现。不要出现未确认的功耗指标、电源门控、时钟门控收益等内容。

## 7. 参考文献规则

参考文献应通过网络检索确认真实数据，采用 GB/T 风格格式。优先使用官方或一手来源，例如 RISC-V 官方规范、PicoRV32 官方仓库、Arm AXI 规范、TensorFlow Lite Micro 官方仓库、LiteRT 量化规范和 NMSIS NN 官方文档。引用条目应包含责任者、题名、文献类型、发布日期或版本日期、访问日期和 URL。

不得使用虚构出版信息、未经确认的标准编号、不可追溯的博客或二手摘要作为核心参考文献。若网页无明确发布日期，可只保留访问日期，但不得自行假设发布日期。

## 8. 插图与附加资产

报告所有附加资产应放在 `doc/original_docx_report_md/` 目录下。正文引用图片时优先使用该目录内的 `report_figures`、`perf_plots`、`figures` 等子目录，避免引用外部临时路径。

架构设计章节需要配图。Mermaid 架构图应使用分明颜色区分 CPU、总线、存储、配置寄存器、NPU 计算、DMA 和状态反馈。状态机图统一使用 Mermaid `stateDiagram-v2`。暂时没有现成图片的位置可以先插入占位图题，并在 `figures_ai_prompts.md` 中补充详细绘图提示词。

绘图 prompt 应准确对应 RTL 实现，说明模块结构、颜色、布局、信号方向、接口字段、时序关系和连接方式。图中文字不能太小，方框元素可以较密集，但所有模块名和信号名必须清晰可读。曲线图和柱状图优先由脚本基于实测数据生成，结构图和流程图可用 AI 绘图提示词生成。

## 9. 文件管理与提交规则

正式报告文件为 `doc/original_docx_report_md/原版报告_技术报告.md`。该文件应只包含规范设计内容，不保存修改日志、迁移记录或验证素材。报告修订记录、验证素材、性能草稿、旧导出备份等应保存在独立文件中，不能混入正式报告正文。

提交文档修改时，应只暂存正式报告、报告引用图片、图源文件、绘图提示词和必要说明文件。RTL、驱动、仿真脚本或其他工作区改动若与文档提交无关，应保留在工作区，不随文档提交一起纳入。

提交前建议运行文本检查，确保正式报告正文不含禁用词、过时术语、未替换的 `Invoke()`、`beat`、`MMA`、`S16/S32/S64` 等不符合当前写法的表述。若检查对象是提示词或知识库，可以保留用于规则说明的禁用词列表，但正式报告正文不得出现。
