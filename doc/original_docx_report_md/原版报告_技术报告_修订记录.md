# 正文审查与修订记录

### 15.8 设计一致性复核与工程化补充

**15.8.1 顶层参数与赛题统计范围复核**：顶层参数是判断报告是否贴合当前项目的第一层证据。`soc_top.sv` 中 AXI-Lite 数据宽度为 32 位，AXI-Lite 地址宽度为 16 位，CPU 原生地址宽度为 32 位，NPU AXI 数据总线默认为 32 位，说明控制面和数据面都围绕 32 位接口组织。`SIZE=16`、`IA_CACHE_BLOCKS=4`、`PS_FRAME_COUNT=SIZE` 是当前默认优化构型，而不是赛题基础 4x4 的唯一构型。报告中因此必须同时写明参数化支持 `SIZE=4` 的基础阵列，以及默认优化配置采用更大阵列。

顶层地址映射也必须与驱动一致。RAM 基址为 `0x00000000`，UART 为 `0x02000000`，NPU AXI-Lite 窗口为 `0x10000000`，SOC 控制窗口为 `0x20000000`。驱动中的 `DSA_MMIO_BASE` 与 NPU 窗口一致，CSR 字地址与 `csr_unit` 的定义一致。若报告只写“CPU 通过寄存器访问 NPU”而不给出窗口关系，就无法证明软件、互连和硬件配置指向同一对象。

顶层还揭示了一个容易被忽略的边界：PicoRV32 的 IRQ 路径在当前系统配置中未启用，而 `mma_axil_top` 仍保留 IRQ 输出和 IRQ mask。本文因此把 NPU 完成通知写成轮询式 done sticky，而不是写成中断驱动。只有当 CPU IRQ 使能、PLIC 或本地中断连接、驱动 ISR 和清中断流程都存在时，才能把中断完成写成已实现能力。

**15.8.2 CPU 桥接与取指路径复核**：`pico_native_to_axi` 的任务是把 PicoRV32 原生 memory interface 转为 AXI。它既要服务指令取值，也要服务数据 load/store 和 MMIO 访问。CPU 写请求在当前桥中以单拍方式发出，适合寄存器写和普通 store；可选指令 cache 打开时，取指路径可以按 cache line 发起 burst 填充。顶层默认关闭指令 cache，因此报告不能把 icache burst 写成默认性能收益，只能写成桥模块具备的可选能力。

CPU 桥接的正确性影响 NPU 启动顺序。驱动写入一组 CSR 后再写 start，如果桥接模块对写响应处理不正确，软件可能在配置尚未提交时启动 NPU。当前设计通过 AXI 写通道和响应通道保持顺序，软件侧再用 fence 约束内存与 MMIO 的可见性。这个层次说明 CPU/NPU 协同不是单纯的一条 start 线，而是由 CPU store、AXI 写事务、寄存器采样和状态轮询共同构成。

桥接模块还决定非法地址访问时 CPU 是否会挂死。互连在非法地址上返回错误响应和固定读值，桥接模块需要把响应正确反馈给 PicoRV32 的 ready/rdata 语义。报告中把非法地址列为边界条件，是因为处理器系统必须能从错误访问中前进，不能让一个错误 MMIO 地址造成永久等待。

**15.8.3 共享互连仲裁复核**：`soc_axi_interconnect` 是共享 AXI 拓扑是否成立的核心。CPU 与 NPU 都可以访问 RAM，但只有 CPU 应该访问 AXI-Lite 外设。互连把地址解码为 RAM、MMA、UART、CTRL 或 ERR，并在 RAM 通道上维护读写 owner、active 标志和 outstanding 计数。这个设计使 NPU 的大块 DMA 与 CPU 的取指、轮询和普通内存访问可以共存。

互连不是简单 mux。读通道和写通道都有事务保持问题：一旦某个 master 的 burst 被接受，后续数据和响应必须返回给正确 owner；如果中途切换 owner，就会发生数据错配。当前 RTL 中的 owner 寄存器、active 标志和 yield 条件正是为了解决这种多拍事务归属问题。报告中把它写成“共享 AXI 互连”时，也要解释 burst 保持和响应归属，否则共享拓扑的工程意义不完整。

互连的统计信号对性能诊断很重要。性能日志中的 CPU 等待、MMA 等待和 yield 次数说明 NPU 与 CPU 确实存在总线竞争。这个竞争不一定是坏事，因为共享 RAM 本身就是赛题要求的异构 SoC 场景；关键在于能够观察并优化竞争。后续若加入更宽总线、多 bank RAM 或优先级策略，也应先用这些计数器判断瓶颈是否真的在互连。

**15.8.4 AXI RAM 与随机延迟复核**：`soc_axi_ram` 在仿真中承担系统主存角色，并支持随机延迟注入。它不是物理 DDR IP，也不是物理存储宏，但它足以验证 AXI burst、outstanding、wstrb、rlast/wlast 和响应等待。带随机延迟的 4x4 用例通过，说明控制器和 DMA 没有依赖零延迟理想内存。

随机延迟验证对 NPU 尤其重要。IA loader、kernel loader、bias loader 和 requant 参数加载都通过 DMA 读取内存，如果读数据晚到，控制器必须等待 valid；如果输出写响应晚到，done 必须延后。没有随机延迟，很多“固定周期推进”的错误不会暴露。报告把随机延迟作为功能验证证据，而不是把它扩大为物理存储性能结论。

AXI RAM 的 wstrb 支持与输出 tail 直接相关。NPU 最终输出 int8 数据，最后一个 beat 可能只有 1、2 或 3 个有效字节。若 RAM 模型不支持 byte strobe，tail mask 相关错误很难被发现。当前输出 FIFO 和 OA writer 生成 mask，RAM 按 mask 写入，构成了尾部写回的完整控制过程验证基础。

**15.8.5 AXI-Lite 寄存器层复核**：`mma_axil_top` 把软件可见寄存器与 NPU 内部信号隔离开来。软件写 CTRL 的 start 位并不会直接长时间保持为内部 start，而是被转换为脉冲；done 与 writeback valid 则是 sticky 语义，需要软件显式清除。这个设计避免 CPU 轮询速度和硬件状态保持时间不匹配。

控制位之间的关系必须清楚。bit0 启动任务，bit8 清 done，bit9 清写回有效；bit1、bit2、bit3 分别选择 IA 16 位、per-channel 和输入固定数据流。驱动通常在启动时同时携带 clear 位，目的是清理上一次任务残留状态。若报告只列寄存器地址而不说明 sticky 与 clear 关系，软件协同流程就会缺少关键时序约束。

状态寄存器同样需要按软件语义解释。ready 表示硬件能接受新任务，busy 表示当前任务尚未完成，done 表示一次任务已经走完输出写回，error code 表示配置或资源问题，response error 表示响应异常。软件应在 done 后检查错误，而不是把 done 等同成功。当前驱动有超时和状态检查路径，这说明系统考虑了 NPU 长时间不完成的异常场景。

**15.8.6 CSR 配置合法性复核**：CSR 单元保存矩阵任务的全部上下文。LHS/RHS/DST/BIAS 地址、K/N/M 维度、三类 stride、zero point、输出 offset、multiplier、shift 和激活范围共同定义一次量化矩阵乘。NPU 控制器依赖这些字段生成 DMA 请求和 tile 循环，因此任何字段不一致都会在硬件内部扩散为地址错误或结果错误。

合法性检查需要区分必须字段和可选字段。输入、权重、输出地址以及 K/N/M、stride 等是基本矩阵乘必须字段；偏置在某些模式下可以为空或 sleep；per-channel 模式下 multiplier 和 shift 地址必须有效。`mma_controller` 中的配置错误码正是为了在 start 后尽早发现这类错误，而不是等到 DMA 访问无效地址后才暴露。

CSR 宽度也影响可扩展性。当前地址和数据寄存器按 32 位组织，适配 PicoRV32 和 32 位 AXI。若未来扩展到更大物理地址空间或 64 位总线，CSR 格式需要调整或增加高位寄存器。本文不把当前 32 位 CSR 写成无限可扩展，而是把它作为当前 SoC 地址范围内的合理设计。

**15.8.7 主控制器状态机复核**：`mma_controller` 的状态包括 IDLE、INIT、WEIGHT_START、IA_START、WEIGHT_WAIT、IA_WAIT、WAIT_WB 和 ERROR。这个状态机不是单纯地先加载权重再加载输入，而是在权重、输入、偏置、量化参数、FIFO 水位和 partial sum tail 之间协调。只有所有必要条件满足，控制器才允许下一阶段推进。

控制器的等待条件体现了流水安全性。`weight_data_valid`、`weight_sending_done`、`ia_data_valid`、`ia_sending_done`、`bias_ready_for_compute`、`quant_params_valid`、`fifo_full_flag`、`oa_calc_over` 和 `partial_sum_calc_over` 等信号共同决定是否继续。若忽略其中任一项，可能导致阵列使用旧权重、IA cache 被覆盖、bias 未准备好、输出 FIFO 溢出或 done 过早。

控制器还记录 stall 与利用率相关信息。仿真中的 `MMA_CTRL_UTIL` 可区分 weight wait、IA wait、bias wait、FIFO wait、tail pending 等原因。这个统计对后续优化比单个总周期更有用，因为它告诉设计者应该增加缓存、调整 tile、扩大 FIFO 还是优化总线。报告中保留这些 stall 名称，是为了让性能分析和 RTL 观察点对应起来。

**15.8.8 IA loader 与输入缓存复核**：IA loader 是当前 NPU 降低访存压力的重点模块。它管理多个 cache block，通过 `blk_valid`、`blk_busy`、`wr_slot_ptr`、`rd_slot_base` 等寄存器控制写入、读取、释放和复用。对于同一组输入 tile，如果后续多个权重组仍要使用，loader 可以避免重复从外存读取。

IA loader 的循环变量体现了多层 tile 结构。`l2_idx`、`l1_idx`、`w_group_idx`、`ia_idx` 等计数器不是随意命名，而是对应输入复用、权重组和 tile 内元素发送顺序。报告中把 L1/L2 解释为 IA loader 内部缓存分组，而不是 CPU cache 层级，可以避免读者误以为这是处理器存储层次。

输入数据还需要在进入阵列前做时序变换。权重固定脉动阵列要求 IA 按对角节奏进入，cache manager 通过 col0 leader 和 shift register 形成阵列所需的数据流。边界 tile 的无效列需要用 zero point 或无效标记处理，否则最后一组输出会混入随机数据。IA loader 因此同时承担地址生成、缓存复用和阵列对齐三类责任。

**15.8.9 kernel loader 与权重布局复核**：kernel loader 读取右矩阵 tile，并把外存中的矩阵布局转成阵列列方向的权重流。为了提高 burst 连续性，权重访问按输出列或组进行组织，DMA base、row stride、valid rows 和 burst length 由当前 tile 位置计算。这个选择服务于 AXI 传输效率，而不是单纯追求最直观的矩阵下标顺序。

权重 buffer 的存在使 DMA 和阵列 store 解耦。DMA 读数据可能受内存延迟影响，而阵列装载权重需要相对稳定的列向量节奏。buffer 让权重加载和发送之间有缓冲，`store_weight_req` 再把权重写入 PE。若没有 buffer，阵列会直接暴露在 AXI R 通道抖动下，随机延迟会让 compute window 难以预测。

权重 loader 也有尾部问题。当输出通道数 M 不是 SIZE 对齐时，最后一组权重列部分有效；当 N 不是 SIZE 对齐时，最后一组乘加行部分有效。硬件需要确保无效权重或输入不会贡献错误 MAC。报告中把权重 loader 与阵列 tail 一起说明，是因为它们共同决定非整齐矩阵的正确性。

**15.8.10 bias loader 复核**：bias loader 按输出通道组读取偏置，并用双 bank 结构支持当前组计算和下一组准备之间的切换。偏置不像 IA 或权重那样每个 MAC 都参与外存访问，但它对每个输出通道的初始累加值至关重要。若偏置组错位，最终分类结果可能完全错误。

bias loader 的状态机包含初始化、组选择、命令发起、请求、加载、等待和下一组切换等阶段。它需要知道当前输出组需要多少 bias 元素，最后一组是否不足 SIZE，以及何时可以标记 `bias_valid`。控制器使用 `bias_sleep` 和 `bias_ready_for_compute` 判断是否等待偏置，因此 bias loader 对 compute start 有直接门控作用。

偏置访问量相对较小，但延迟不能被忽视。在小矩阵或 tail 较多的模型中，偏置和量化参数加载可能占据可见比例。后续如果加入更强的预取策略，可以让 bias loader 在上一组计算尚未结束时提前加载下一组，从而减少控制器在 bias wait 上的停顿。

**15.8.11 计算核心与脉动阵列复核**：compute core 连接 bias mux、权重固定阵列和 partial sum buffer，是 NPU 的主要计算段。阵列内部每个 PE 保存权重、寄存输入、执行乘法并累加上方传入的 partial sum。这个结构简单稳定，适合综合和参数化复制。

阵列的尾部 flush 是报告必须写清的细节。即使最后一拍 IA 已经送入，partial sum 仍需要若干周期穿过阵列到达底部。RTL 中用 tail 计数、tile start pipe 和 partial sum done 信号保证输出侧不会提前消费无效结果。若以为输入发送完就等于计算完成，就会错误设置 done 或覆盖 ps buffer。

计算核心对峰值的贡献可以明确量化：每周期最多 SIZE×SIZE 个 MAC，按 1MAC=2ops 计算。报告中所有 TOPS/GOPS 都从这个结构出发，而不是从模型操作数或循环次数随意推导。这样可以保证基础 4x4、默认 S16 和探索 S32 的峰值统计范围一致。

**15.8.12 partial sum buffer 复核**：partial sum buffer 的作用是在跨 tile 累加时避免把中间和写回外存。矩阵乘的 N 维被分块后，同一个输出元素需要多次部分乘加。如果每次都把 int32 partial sum 写入 RAM，再从 RAM 读回继续累加，外存带宽会成为绝对瓶颈。

`ps_buffer` 使用宽 FIFO 或伪双口 RAM 保存 frame，并通过 de-diagonalizer 调整阵列输出顺序。它需要响应 `replay_enable`、`ia_l1_switch` 和 `send_ia_trigger`，在下一轮计算时把已有 partial sum 送回阵列或计算核心。这个过程对时序要求高，因为 replay 的 partial sum 必须与新的 IA/weight 乘积在同一输出元素上对齐。

PS frame 数与 IA 复用、阵列大小有耦合关系。`PS_FRAME_COUNT=SIZE` 是当前默认选择之一，后续若改变 SIZE 或 IA cache 数量，需要重新确认 ps buffer 深度是否足够。报告把它列为扩展限制，是为了避免误以为只改顶层 SIZE 就能线性扩展所有内部存储。

**15.8.13 vec_requant 复核**：requant 模块把 int32 累加结果变成 int8 输出，是 AI 推理而非纯矩阵乘演示的关键。它处理 multiplier、shift、dst offset、activation min/max 和饱和。per-tensor 模式下参数可视为标量，per-channel 模式下需要按输出通道读取参数数组。

内部流水包含多级乘法、移位、舍入和裁剪。为了适配硬件资源，乘法可拆成部分积，移位分左移和右移，舍入需要考虑符号和阈值。输出端必须保证 stage valid 与数据对齐，不能让某一 lane 的参数错用到另一 lane。报告中写 12 级左右流水，是为了说明 done 需要覆盖 requant 尾部，而不是阵列输出后一拍就结束。

per-channel 参数加载会产生额外 DMA 读流量。对于输出通道较多的层，multiplier 和 shift 数组访问会影响总线；对于小层，参数加载和配置开销可能压过计算收益。后续性能计数器应将量化参数读字节单独统计，以便判断 per-channel 模式的真实成本。

**15.8.14 输出 FIFO 与打包复核**：`vec_s8_to_fifo` 把 requant 产生的 int8 lane 打包成 32 位输出 beat。由于总线宽度为 4 byte，四个 int8 可以组成一个完整 beat；最后不足四个时用 byte mask 表示有效字节。这个模块把 AI 量化输出和 AXI 写协议连接起来。

FIFO bank 的存在使 requant 和 OA writer 解耦。requant 输出节奏取决于计算流水，OA writer 写回节奏取决于 AXI AW/W/B 通道和 RAM 响应。若没有 FIFO，写通道短暂停顿就会反压到 requant 和阵列。当前 FIFO 通过 bank ready、count、水位和 full 标志把反压传回控制器，避免溢出。

转置模式与输入固定数据流相关。某些数据流下，阵列输出的自然顺序与目标内存布局不同，FIFO 或写回路径需要调整行列顺序。报告不把转置写成独立功能炫技，而是把它放在 IS 模式的配套路径中说明。

**15.8.15 OA writer 复核**：OA writer 负责最终输出矩阵写回。它根据 dst base、dst row stride、tile 行列位置、有效行列数和 burst 长度生成 DMA 写命令，并从输出 FIFO 消费数据。写回地址必须与软件期望的 tensor layout 完全一致，否则后续算子会读取错位输出。

输出写回的 tail 处理包含两个层面。行或列不足 SIZE 时，OA writer 要减少 rows_to_write 或 valid columns；每行最后一个 32 位 beat 不满时，要配合 output mask。对于 int8 输出，这两个 tail 常常同时出现。当前设计把 mask 传给 DMA 写引擎，再由 AXI wstrb 写入 RAM，形成完整保护。

OA writer 的 done 是 NPU done 的重要前置条件。只有写命令发出、数据 beat 被接受并收到写响应后，输出才算对 CPU 可见。报告中把 `oa_calc_over` 和 `write_done` 放入控制器等待条件，是为了避免把阵列计算完成误认为任务完成。

**15.8.16 DMA 仲裁器复核**：`axi_block_dma_arbiter` 将多个读客户端和一个写客户端接入共享双向 DMA。读客户端包括 IA、权重、偏置和量化参数，写客户端主要是输出写回。仲裁器需要把不同模块的命令转换为统一 DMA 字段，并把完成信号返回给正确模块。

仲裁策略影响阵列利用率。若 IA 请求长期得不到服务，阵列缺输入；若权重请求长期得不到服务，store_weight 阶段停顿；若量化参数滞后，requant 不能输出；若输出写回拥塞，FIFO full 反压计算。仲裁器因此不仅是协议 glue，也是性能调度点。

当前设计将 DMA 作为 NPU 内部引擎，而不是单独暴露给 CPU 的可编程 DMA 外设。报告中把“DMA 完成”限定为内部块 DMA 完成，避免读者误解为系统中存在一个独立、通用、由 CPU 配置源/目的/长度的 DMA 控制器。

**15.8.17 双向块 DMA 复核**：`axi_dual_block_dma` 支持二维读写、burst、outstanding、非对齐和数据格式转换。读引擎根据 base、row stride、rows、valid cols 和 burst length 发起 AR，并在 R 通道返回后解包 s8/s16 数据。写引擎根据输出 base、stride、rows 和 mask 发起 AW/W，并等待 B 响应。

非对齐处理是工程实现中的难点。矩阵地址不一定按 4 byte 对齐，读请求可能跨 beat，写请求可能只覆盖一个 beat 的部分字节。DMA 需要把地址向下对齐、合并前后 beat 或生成正确 mask。报告中强调这一点，是因为很多简单演示只支持对齐访问，而真实 TFLM buffer 不应被硬件强制过度约束。

outstanding 能力提高了随机延迟下的吞吐。读引擎在条件允许时保持多个请求在途，减少等待单个响应的空泡。与此同时，outstanding 也带来顺序和资源计数问题，必须确保返回数据对应正确行、slot 和元素位置。当前 trace 统计中的最大 outstanding 和 unaligned/cross 计数是后续分析 DMA 行为的重要依据。

**15.8.18 软件算子映射复核**：全连接算子映射最直接，batch 为 K，输入通道为 N，输出通道为 M。权重矩阵、偏置、量化参数和激活范围都能自然填入 DSA 配置。MLP 性能提升显著，正是因为模型主要由这种大块规则矩阵乘构成。

卷积算子通过 im2col 进入硬件矩阵乘。这个路径的优点是硬件复用度高，不必为每种 kernel、stride、padding 单独做卷积控制器；缺点是 im2col buffer 需要额外内存和 CPU 工作。CNN 加速比低于 MLP，说明软件展开和非矩阵算子开销在端到端路径中不可忽略。

NMSIS-NN ExtraAcc 封装层的价值在于保持上层 API 语义。调用者仍然使用软件库形式的函数入口，内部根据配置把矩阵乘交给 NPU。后续如果增加硬件支持范围，最好继续保持这一层抽象，让模型代码不感知硬件寄存器细节。

**15.8.19 性能计数统计范围复核**：报告中的 GOPS、TOPS、带宽利用率和 busy ratio 必须来自同一时间窗口。理论峰值可由 SIZE 和频率直接计算，但实际 GOPS 需要知道任务操作数和任务周期；带宽利用率需要知道读写字节和任务时间；计算利用率需要知道实际 MAC 数和峰值 MAC/cycle。不同日志里的统计不能随意拼接成一个达标数字。

现有固定扫描中的 read beat/active 与 write beat/active 可以用来诊断访存压力，但不能直接等同于官方带宽利用率。原因是 beat 占用是周期占比或活动窗口指标，而带宽利用率是字节/秒与峰值字节/秒的比值。若要最终申报 60% 或 80%，需要在同一仿真中输出 read_bytes、write_bytes、npu_cycle_count 和 bus_freq_hz。

计算利用率也要区分 active 与端到端。MMA active GOPS 描述阵列活跃窗口内的计算效率，SoC GOPS 描述包含配置、等待、DMA 和写回的端到端效率。S16/C16 的 active GOPS 高于 SoC GOPS，说明数据搬运和控制开销仍然显著。报告同时给出这两个统计范围，可以避免只展示更好看的单一数字。

**15.8.20 验证矩阵复核**：当前已有 4x4 随机、固定尺寸/缓存扫描、MNIST MLP 和 MNIST CNN 证据。这些测试覆盖了基础阵列、较大阵列、随机延迟、矩阵尺寸变化、端到端模型调用和软件驱动路径。它们足以支持“功能完整控制过程已建立”的结论。

仍需补充的验证包括非法配置、空指针、零维度、stride 为零、per-channel 参数缺失、AXI 错误响应、FIFO 满、水位边界、非对齐跨 beat、最大 outstanding、CPU 与 NPU 高冲突、IS 模式全面组合和极小矩阵。没有这些覆盖时，报告不能声称达到高覆盖率或完全鲁棒。

覆盖率 95% 是一个独立证据项，不应由测试通过数量替代。代码覆盖、功能覆盖和断言覆盖各自回答不同问题：代码是否执行过，关键场景是否覆盖过，协议性质是否被持续检查。当前材料没有覆盖率汇总，因此本文如实写为待补充。

**15.8.21 迁移一致性复核**：本报告已将主题统一为 PicoRV32 与优化 NPU 的异构处理器。正文中的模块名、参数、寄存器和性能数据均来自当前 RTL、驱动和文档；旧项目应用假设不再作为技术论据。这样做的目的不是抹去历史文件，而是让交付物对新赛题负责。

迁移后最容易出现的不一致是标题与正文不一致、CPU 名称不一致、接口协议不一致和性能统计范围不一致。本文使用 PicoRV32、AXI-Lite、AXI Burst、`mma_top`、`ws_systolic_array`、`axi_dual_block_dma` 等当前项目术语，并在算力处固定 1MAC=2ops 统计范围，避免将旧报告语境残留到新报告。

另一个一致性要求是限制与完成情况要相互匹配。若前文说低功耗未实现，指标表中也必须写未实现；若前文说 S32 仍未达到 0.5TOPS，后文不能再宣称 NPU 已满足 0.5TOPS。本文把这些限制集中列出，是为了让评审能清楚地区分已完成工程、部分完成探索和后续工作。

**15.8.22 后续实施顺序建议**：若继续推进项目，第一优先级应是完善性能计数器和覆盖率。没有统一计数器，就难以判断总线优化是否有效；没有覆盖率，就难以证明复杂状态机和边界路径已经充分验证。计数器和覆盖率是后续优化的测量基础。

第二优先级是带宽与缓存协同优化。S16/C16 的结果显示当前平衡点还有提升空间，S32/C4 的结果说明只扩大阵列不可取。可尝试更宽 AXI、更多 IA cache、权重预取、读写优先级调度和更细粒度 stall 反馈，目标是提高端到端 SoC GOPS，而不是单纯提高理论峰值。

第三优先级是低功耗真实落地。先从模块级 clock enable 开始，围绕控制器状态、DMA 活跃、loader 活跃、阵列 compute window、requant valid 和 FIFO 非空生成门控条件；再通过仿真波形统计切换；最后再讨论 DFS 或多电源域。这样能把“减少数据搬运”的架构动机转化为可验证的功耗证据。

第四优先级是软件算子融合。对于 CNN，im2col 和非矩阵算子限制了端到端加速。可以考虑硬件滑窗 loader、卷积专用地址生成、池化融合或更大的 im2col 批量策略。软件与硬件共同优化，才可能让模型级速度接近矩阵乘内核的速度提升。

边界与验证关注：本条目需要重点检查零长度任务、尾部 tile、非对齐地址、随机内存延迟、FIFO 满或空、错误响应、重复 start、清状态位和复用参数越界等情况。当前已有回归覆盖了部分正常路径和模型路径，但并不意味着所有边界都覆盖。报告在完成情况表中保留覆盖率待补充，就是为了把功能通过与覆盖充分区分开。

性能影响说明：该条目对性能的影响可以表现为减少外存访问、提高 burst 连续性、降低 CPU 轮询或搬运开销、维持阵列输入供给、减少输出写回字节数，或暴露总线争用。若后续优化只观察最终周期而不拆分到这些模块，就很难判断瓶颈来自 DMA、互连、缓存、阵列尾部、量化参数加载还是软件展开。

扩展限制说明：扩展该条目时必须同步考虑上下游。例如扩大阵列需要更多输入和权重供给，扩大 DMA outstanding 需要更多响应跟踪资源，扩大 AXI 宽度需要修改打包和 mask，增加动态配置需要软件查询和非法组合处理。报告把这些限制写入正文，是为了避免把参数化 RTL 误解为没有代价的运行时可重构。

### 15.10 性能与验证数据的逐项解释

**MLP 加速数据解释**：MNIST MLP 的硬件平均 invoke 周期约 443903，软件平均约 44126602，约 99.4 倍。这个加速来自全连接层高度规则的矩阵乘结构，输入、权重和输出都能映射到 NPU 的 GEMM 数据流。由于全连接层占模型计算比例高，配置开销、轮询开销和输出写回开销被较大的 MAC 数摊薄，因此端到端收益接近硬件矩阵乘本身的收益。

MLP 结果不能直接外推到所有网络。若模型由大量小矩阵、分支、查表或非矩阵算子构成，NPU 启动开销和软件调度开销会更显著。报告中把 MLP 与 CNN 分开说明，就是为了避免把一个高度适配 GEMM 的模型结果写成所有 AI 推理的统一加速比。

**CNN 加速数据解释**：MNIST CNN 的硬件平均 invoke 周期约 4200423，样例软件周期约 60410324，对应约 14.39 倍。CNN 中卷积需要 im2col，池化和其他小算子仍由软件执行，且每层 shape 变化更多，因此 NPU 不能覆盖全部执行时间。这个结果仍然证明硬件路径有效，但也提示算子融合和数据重排是后续提升重点。

CNN 路径还说明端到端推理不只取决于 NPU 峰值。即使矩阵乘内核很快，im2col buffer 的写入、输入 patch 组织、输出 layout 处理和层间同步都会消耗 CPU 周期和内存带宽。后续若要提高 CNN 加速比，应优先减少 im2col 额外流量，而不是单纯扩大 MAC 阵列。

**固定尺寸扫描解释**：S4/C256、S8/C64、S16/C16、S32/C4 的扫描结果表明，在固定 IA cache 容量下，阵列规模与缓存深度存在平衡。S4 active utilization 高但峰值低，S32 峰值高但供给不足，S16 在 512^3 下取得较好 SoC GOPS。这个结论对架构选择很重要，因为赛题关注的是有效异构处理器，不只是单模块理论峰值。

扫描表中的 read beat/active 与 write beat/active 也说明访存压力随阵列规模增长。S16/C16 的读占用已经明显高于 S4/C256，S32/C4 更受读侧限制。若未来要继续扩大阵列，必须同步提高总线宽度、缓存命中、预取深度或数据复用，否则新增 PE 会更多时间等待数据。

**4x4 基础验证解释**：4x4 随机用例在随机 DDR 延迟条件下通过，证明基础 SIZE=4 构型的控制、DMA、阵列和写回路径能够在非理想等待下完成任务。这个证据对应赛题基础要求，但它的性能数字不能代表默认优化构型。报告中将 4x4 作为基础正确性，将 S16/S32 作为参数化优化探索，是为了保持证据边界清晰。

4x4 的理论峰值只有 6.4GOPS，适合作为小面积功能基线。若评审关注 0.5TOPS 指标，必须转向更大阵列、更高频率或并行阵列。当前项目没有达到这一指标，本文在指标表中明确写为未达成。

**总线统计解释**：现有日志中的 `cpu_ar_wait`、`mma_ar_wait`、`rd_yield`、`wr_yield` 反映 CPU 与 NPU 在共享 RAM 上的竞争。AXI 统计中的 AR、R、AW、W、B 计数反映 DMA 请求和数据返回规模。这些统计可用于定位瓶颈，例如读等待多说明输入或权重供给不足，写等待多说明输出 FIFO 或 RAM 写响应可能限制流水。

但这些统计还不足以直接给出官方带宽利用率。官方公式需要读写字节、任务周期、总线宽度和频率；若只用 beat/active，就可能忽略任务窗口、空闲周期或读写方向差异。本文把总线指标写成部分验证和待补充精确计数，是对现有证据的保守解释。

**覆盖率解释**：测试通过不等于覆盖率达标。当前材料中的 PASS 记录说明一批用例正确，但覆盖率 95% 需要代码覆盖、功能覆盖或断言覆盖报告。尤其是 AXI 错误响应、非法 CSR、FIFO full、非对齐跨 beat、per-channel 参数缺失、IS 模式边界和重复 start 等路径，不一定被模型样例自然触发。

后续覆盖率工作应围绕模块和系统两层展开。模块层覆盖状态机转移、边界计数器、tail mask、错误码和 ready/valid 反压；系统层覆盖 CPU 配置、DMA 访问、互连仲裁、模型推理和超时恢复。只有这两层数据完整，才能把“功能回归通过”升级为“验证覆盖充分”。

**低功耗解释**：当前架构减少了重复访存，理论上有利于能效，但没有实现可证明的低功耗机制。clock gating 需要明确的时钟使能、门控插入和无毛刺验证；DFS 需要频率切换安全点和跨域处理；功耗结论需要切换活动和功耗模型。本文把低功耗写为未实现，是为了避免把性能优化和功耗达标混为一谈。

如果后续要补低功耗，建议先从可验证的 clock enable 开始，而不是直接声明复杂电源管理。控制器 idle、loader idle、DMA idle、array idle、requant idle 和 FIFO empty 都可以形成门控候选条件。每个条件都应有仿真断言，保证停钟不会丢失握手或状态。

**软件一致性解释**：驱动、CSR 和 RTL 的一致性是端到端成功的前提。`dsa_accel.h/c` 中的寄存器偏移、控制位、状态位和 CSR 地址必须与 `mma_axil_top`、`csr_unit` 保持一致。TFLM/NMSIS-NN 适配层再把算子参数映射到这些字段。任何一层的字段顺序错误都可能导致硬件正常运行但结果错误。

软件还需要处理超时和错误。NPU 可能因为非法配置、总线响应错误或内部资源等待而无法正常完成，驱动轮询必须有上限，并在完成后检查错误位。当前 `dsa_matmul_execute` 的超时和状态读取体现了这种防御性设计，报告中将其作为软件接口的一部分说明。

**后续性能目标解释**：若目标是接近或超过 0.5TOPS，单个 S32@200MHz 仍不足，需要扩大阵列或提高频率。扩大阵列同时需要更宽总线和更多缓存，否则 active utilization 会下降。若目标是提高模型端到端速度，则可能优先优化 im2col、算子融合、软件调度和内存布局，而不是只提高峰值。

若目标是总线利用率达标，首先要补齐计数器，然后根据读写占比选择策略。读侧瓶颈可用更大 IA cache、权重预取、较长 burst 或更宽 AXI 缓解；写侧瓶颈可用更深 output FIFO、合并写、减少尾部碎片和优化 layout 缓解。没有计数器时，优化容易依赖猜测。

### 15.11 最终审查清单与交付统计范围

**架构统计范围审查**：本文最终采用的架构统计范围是“PicoRV32 控制面 + AXI 共享互连 + 参数化矩阵乘 NPU + TFLM/NMSIS-NN 软件接入”。所有章节都围绕这个统计范围展开，没有把单独的阵列模块误写成完整处理器，也没有把软件模型测试误写成硬件微架构本身。CPU 的角色被限定为任务配置、运行时调度、异常检查和非加速算子执行；NPU 的角色被限定为矩阵乘、量化输出和 AXI 主动搬运。这个边界有助于评审判断哪些能力属于处理器系统，哪些能力属于加速器内部流水。

**证据统计范围审查**：正文中使用的模块名、寄存器、状态和性能数据都来自当前已读 RTL、驱动和文档。对于无法从材料中证明的内容，报告使用“未实现”“待补充”或“部分完成”表述。例如低功耗没有写成完成，覆盖率没有写成达到 95%，运行时动态阵列没有写成实现，总线带宽没有写成确定达标，0.5TOPS 没有写成完成。这些保守表述不是弱化项目，而是保证报告和工程证据一致。

**算力统计范围审查**：所有峰值计算统一采用 1MAC=2ops。4x4@200MHz 为 6.4GOPS，S16@200MHz 为 102.4GOPS，S32@200MHz 为 409.6GOPS。报告没有用模型总操作数、循环次数、并行仿真配置或非标准换算放大 TOPS。实际性能则区分 MMA active GOPS 与 SoC GOPS，避免把阵列活跃窗口性能当作端到端处理器性能。这个统计范围对后续优化也很重要，因为它能清楚说明瓶颈来自峰值不足、访存不足还是软件开销。

**总线统计范围审查**：报告把 AXI-Lite 控制和 AXI burst 数据分开说明。AXI-Lite 负责寄存器与 CSR，适合单拍配置；AXI burst 负责 IA、权重、偏置、量化参数和输出写回，适合矩阵 tile。互连章节解释了 CPU 与 NPU 共享 RAM 的 owner、outstanding 和错误响应，DMA 章节解释了二维地址生成、非对齐、mask 和响应等待。带宽公式已经给出，但达标结论保留为待补充精确计数，避免用 beat 占用近似值替代官方字节带宽。

**软件统计范围审查**：驱动层被写成当前项目的必要组成，而不是附带脚本。`dsa_matmul_execute` 的 CSR 写入、复用配置、fence、start、poll、timeout 和错误检查构成 CPU/NPU 协同的真实软件路径。TFLM/NMSIS-NN 接入说明了全连接和卷积如何映射到硬件，其中卷积通过 im2col 带来额外开销。这个叙述能解释为什么 MLP 加速比高于 CNN，也能解释后续算子融合的价值。

**模块统计范围审查**：关键模块章节覆盖了顶层、CPU 桥、互连、RAM、AXI-Lite 顶层、CSR、主控制器、IA loader、kernel loader、bias loader、compute core、脉动阵列、PE、partial sum buffer、requant、输出 FIFO、OA writer、DMA 仲裁器、双向块 DMA 和软件接入。每个模块都按“功能说明、结构组成、接口定义、工作流程与状态机、时序行为、寄存器与配置说明”六个小节展开。虽然不同模块的复杂度不同，但正文没有只描述 NPU 框图而忽略真正决定系统完整控制过程的 DMA、互连和软件。

**验证统计范围审查**：报告引用的验证证据包括 4x4 随机用例、固定尺寸/缓存扫描、MNIST MLP 和 MNIST CNN。它们证明了基础阵列、优化构型、随机延迟、软件驱动和模型路径的可运行性。报告同时指出非法配置、协议错误、覆盖率、边界尺寸、FIFO 极限、IS 模式组合和精确性能计数仍需补充。这样的写法使验证结论既能体现已有工作，也不会越过证据边界。

**交付统计范围审查**：本文作为设计报告，重点是赛题理解、架构设计、RTL 模块、软件接口、性能解释和指标完成情况。附录中的 WaveDrom JSON 和绘图 Prompt 只作为图表生成辅助，不计入正文目标。正文中保留了足够的模块审阅记录和工程解释，使它不是摘要版说明，而是能够支撑评审阅读、代码追溯和后续迭代的完整迁移稿。

### 15.12 指标逐项自查补充

**CPU 集成自查**：报告把 CPU 集成写成 PicoRV32 实例、native-to-AXI 桥、共享互连和 MMIO 软件路径的组合，而不是只说“使用 RISC-V CPU”。这种写法对应实际 RTL：CPU 原生请求先进入桥接模块，再由 AXI 互连分发到 RAM 或外设。软件驱动能够在 CPU 上用普通 load/store 写 NPU 寄存器，说明 CPU 与 NPU 处在同一可编程地址空间内。若没有这条路径，即使 NPU 单独仿真通过，也不能算作异构处理器集成。

**NPU 控制自查**：报告把 NPU 控制写成 AXI-Lite 寄存器和 CSR 两级。AXI-Lite 层负责 start、clear、status、reuse 和写回信息；CSR 层保存矩阵乘的地址、维度、stride 与量化参数。这样划分符合软件实际调用：驱动先写 CSR，再写复用和控制位，最后轮询状态。控制自查的重点是 start 不能早于配置，done 不能早于写回，error 不能被软件忽略。

**4x4 阵列自查**：报告没有把默认 S16 配置冒充为基础 4x4，也没有把 4x4 的功能通过写成高峰值达标。`ws_systolic_array` 的参数化 generate 能构成 4x4 阵列，4x4 随机日志提供基础验证；默认优化构型则用于更高性能探索。这个区分很重要，因为赛题基础要求和优化方向的证据不同，混写会造成指标判断混乱。

**AXI Burst 自查**：报告把 burst 能力落到 `axi_dual_block_dma` 的 AR/R 和 AW/W/B 通道，而不是只在总体框图上画一根 AXI 线。读路径有 base、stride、rows、valid cols、burst length 和 outstanding；写路径有 output mask、tail、stride 和响应等待。DMA 能把二维矩阵 tile 转成多行 burst，这是矩阵计算性能的关键。如果只支持单 beat，即使协议名叫 AXI，也难以满足 NPU 数据供给。

**共享总线自查**：报告写明 CPU 与 NPU 共用 RAM，外设由 CPU 地址窗口访问，互连负责 RAM 访问仲裁和外设解码。共享总线不是所有 master 任意访问所有 slave，而是有明确访问权限和错误响应。NPU DMA 主要访问 RAM，CPU 访问 RAM 和 MMIO。这个边界能防止 NPU 意外写控制寄存器，也能让非法地址得到可观察错误。

**DMA 自查**：报告把 DMA 表述为 NPU 内部块 DMA，而不是独立系统 DMA 外设。这个限定符合 RTL：IA、权重、偏置、量化参数和输出写回通过仲裁器共享 `axi_dual_block_dma`，CPU 不直接配置一个通用 DMA 描述符队列。这样写既承认 DMA 能力，也避免超出实现范围。后续若要加入 CPU 可编程 DMA，需要另行定义寄存器、通道、描述符和中断。

**量化推理自查**：报告没有把 NPU 简化成纯 int32 GEMM，而是说明 bias、multiplier、shift、offset、activation clamp 和 int8 saturation。TFLite Micro/NMSIS-NN 的 int8 推理需要这些步骤，否则硬件输出不能直接作为下一层输入。requant 和输出打包使 NPU 的结果更接近真实模型运行，而不是只停留在算法作业式矩阵乘。

**性能自查**：报告同时给出理论峰值、MMA active、SoC GOPS、模型周期和加速比，并解释它们的差别。理论峰值来自阵列规模和频率；active 反映阵列活跃窗口；SoC GOPS 包含更多控制和访存开销；模型周期包含软件运行时和非矩阵算子。多统计范围并列能避免选择单一最好看的数字，也能让后续优化知道目标是提高阵列利用率还是减少系统开销。

**带宽自查**：报告保留了带宽公式，并明确现有 beat/active 统计不能直接替代精确字节带宽。这个结论虽然保守，但符合工程证据。若未来要证明 60% 或 80% 带宽利用率，需要补充 read bytes、write bytes、npu_cycle_count、bus_width_bytes 和 bus_freq_hz 的同窗口计数。没有这些字段，任何达标百分比都容易被质疑。

**低功耗自查**：报告把已实现的“减少数据搬运”与未实现的“低功耗机制”分开。缓存复用、权重固定、partial sum buffer 和打包写回有助于能效，但不等同 clock gating、DFS 或功耗分析。当前没有门控单元、频率切换控制或功耗报告，因此低功耗写为未实现。这个判断能防止把架构优化误写成物理功耗达标。

**验证自查**：报告引用的 PASS 用例覆盖正常功能和模型路径，但没有替代覆盖率报告。功能仿真证明“这些场景能跑通”，覆盖率证明“足够多的代码和场景被检查”。二者不能互换。报告中保留覆盖率待补充，使验证结论与材料一致，也为后续增加断言、随机测试和 covergroup 留出明确工作项。

**可扩展性自查**：报告把参数化和运行时动态配置分开。当前 RTL 可通过参数选择 SIZE、cache 和 frame，但运行时不能改变 PE 数、关闭子阵列或重构拓扑。软件可以改变矩阵维度和复用参数，却不能把 16x16 阵列动态变成多个独立小阵列。这个边界影响加分项判断，因此必须在设计报告里明确说明。

**模型路径自查**：报告把 MLP 与 CNN 分别分析。MLP 主要由全连接构成，矩阵乘占比高，所以加速比高；CNN 需要 im2col、池化和多层控制，端到端加速比低。这个差异说明当前硬件对 GEMM 友好，对卷积仍依赖软件展开。后续若要提高 CNN 性能，应优先减少 im2col 流量和算子间同步，而不是只扩大阵列。

**交付完整性自查**：报告的正文结构覆盖赛题理解、指标映射、SoC 架构、AXI、NPU、阵列、模块、低功耗、性能、寄存器、协同、软件、测试、指标和限制。附录只放图表脚本、Prompt 和资料路径，正文字符统计排除这些内容后仍超过要求。这个结构能满足“在原报告文档基础上迁移为新赛题报告”的目标，也便于后续继续补验证或图表。
